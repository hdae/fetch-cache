## 詳細指摘

### B-1 (W) 長さフィールド上位 32bit（入力 > 512MiB）が自動テストで凍結されていない

- **概要（挙動 + 発生条件）**: `hex()` は総入力長のビット長を上位 / 下位に分けて書く
  （`src/sha256.ts:156-157`）。上位語 `Math.floor(totalBytes / 0x20000000)` が非ゼロになるのは
  `totalBytes >= 512MiB` のときだけで、現行テストの最大サイズは 100003 バイト
  （`src/sha256.test.ts:46`）。つまり**上位語の式を丸ごと落としても既存テストは全部緑になる**。
  実装は現時点で正しい（検証手順 3 で 1GiB+1 まで一致を実証）が、この領域は
  `prefetchUrl` の本命ワークロード（数 GB のモデル）が必ず通る唯一の場所であり、ここが壊れると
  「prefetch が常に sha256 不一致で throw する（= 数 GB DL 後に必ず失敗）」か、より悪くは
  「不正な検証済みマーカーは焼けないので機能停止」になる。テスト冒頭の NOTE
  （`src/sha256.test.ts:41-45`）は「実装時に単発で native と突合して一致を確認済み」と書いており、
  作者もこの穴を自覚した上で意図的に外している — つまり**未知のバグではなく既知の未凍結領域**。

  **証拠（ミューテーション試験の実測）** — 各欠陥を注入して既存 4 テストを走らせた結果:

  | 注入した欠陥 | 対象 | 既存テストの結果 |
  | --- | --- | --- |
  | `previous >>> 3` → `>> 3`（σ0 の符号） | sha256.ts:65 | 4 failed（殺せる） |
  | `recent >>> 10` → `>> 10`（σ1 の符号） | sha256.ts:66 | 4 failed |
  | `word >>> bits` → `>> bits`（rotr の符号） | sha256.ts:44 | 4 failed |
  | K[0] と K[1] を入れ替え | sha256.ts:16 | 4 failed |
  | H(0)[0] を +1 | sha256.ts:37 | 4 failed |
  | `pending < BLOCK_BYTES - 8` → `<=`（tail 境界） | sha256.ts:150 | 1 failed（殺せる） |
  | `state.slice()` → `state`（hex が状態を消費） | sha256.ts:160 | 1 failed（殺せる） |
  | `if (pending < BLOCK_BYTES) return;` → `<=`（保留 flush 抜け） | sha256.ts:134 | 3 failed |
  | **`Math.floor(totalBytes / 0x20000000)` → `0`（上位語を落とす）** | **sha256.ts:156** | **4 passed = 生存** |
  | （対照）無変更 | — | 4 passed |

  生存したミュータントに 512MiB の突合を当てると即死する（実測 2.42s / RAM ~64KiB）:
  `5aba06c3fae03000…` != 正解 `aeea70ef9a7aa996…`。

- **修正案**:
  1. ★**512MiB の golden vector テストを 1 本足す**。64KiB の決定的パターンを**同じバッファを
     使い回して** update するので RAM は ~64KiB、実測 2.4s。期待値は独立実装（node crypto
     または一度きりの native 突合）で凍結した hex 定数を直書きし、「native と比べる」形にしない
     （512MiB の連続バッファ確保を避けるため）。上位語 = 1 になる `0x20000000` ちょうどが最小
     コストで最大の情報を持つ。
  2. 1 と同じ内容を `Deno.test({ ignore: !Deno.env.get("FETCH_CACHE_SLOW_TESTS") })` で
     opt-in にする。`deno task check` の既定 `deno test --allow-read` は +2.4s しないが、
     CI で env を立てないと結局回らない（穴が残るリスク）。
  3. 現状維持 + `src/sha256.test.ts:41-45` の NOTE と ADR 0005:146 に「差分テストの凍結範囲は
     ≤ 100003 バイト。> 512MiB は手動突合のみ」と範囲を明記するだけに留める。
- **リスク**: 案 1 は `deno task check` が +2.4s（現状 sha256 スイートは 16ms、リポ全体でも
  秒未満なので体感差は出る）。案 2 は環境変数の設定漏れで実質案 3 に退行する。案 3 は
  「壊れたら数 GB DL 後に必ず失敗」という故障モードを人手の記憶だけで守ることになる。
  いずれも公開 API・実行時依存には無影響（テストのみ）。
- **対象**: `src/sha256.test.ts:39-46`（SIZES と NOTE）/ 影響する実装行は
  `src/sha256.ts:156`。
- **影響範囲**: テストのみ。`prefetchUrl` / `prefetchHfFile` の数 GB 経路の回帰検出力。
- **引き継ぎ（実装者向け）**: パターンは `pat[i] = (i * 37 + 11) & 0xff` の 64KiB でよい
  （`update(pat)` を 8192 回 → ちょうど 0x20000000）。上のとおり期待値は
  `aeea70ef9a7aa9961135eb4f88af4cd94b34aad65cf8989f00528e8b6c13571d`
  （node `crypto.createHash("sha256")` の streaming と本実装で独立に一致確認済み。
  別パターンを使うなら期待値も取り直すこと）。最後の端数チャンクを混ぜた
  `0x20000000 + 12345` = `3b303cd36ede56bfe1c756f641be917943163bed7de55c99e27876266eff51db`
  を足すと「上位語 + 端数 tail」の組合せも押さえられるが、時間は倍になる。
- **裁定（閉じた選択肢）**: **(a) 案 1（常時実行の 512MiB 凍結テスト、+2.4s）** /
  **(b) 案 2（env gate の opt-in）** / **(c) 案 3（docs に範囲を明記するだけ）**。
  リリース可否そのものはブロックしない（実装の正しさは本レビューで実証済み）。

### B-2 (W) `update()` が「呼び出し後にチャンクを保持しない」ことが契約として書かれていない

- **概要（挙動 + 発生条件）**: `prefetchUrl` は TransformStream の中で
  `hasher?.update(chunk)` してから `controller.enqueue(chunk)` する（`src/mod.ts:632-634`）。
  enqueue した Uint8Array は下流（`cache.put` の実装）が transfer / detach したり、上流が
  バッファを再利用したりしうるので、**`update` がリターン後もチャンクを参照していたら
  静かに誤ったダイジェストになる**。現状の実装はこの性質を満たしている — `update` は
  64 バイトブロックを同期的に `compress` し切り、余りだけを `partial` に**コピー**する
  （`src/sha256.ts:138-145`）。つまり依存は成立しているが、**`Sha256Hasher.update` の JSDoc
  （`src/sha256.ts:109`）は「チャンクを取り込む（分割位置は結果に影響しない）」としか言っておらず、
  非保持は書かれていない**。将来「大きいチャンクは参照だけ持って遅延処理」といった最適化を
  入れると、テストは全部緑のまま prefetch 経路だけが壊れる（テストは呼び出し後にバッファを
  書き換えないため検出できない）。

  ```
  prefetchUrl の通過中検証（src/mod.ts:628-643）
  ┌ response.body ─┐   transform(chunk)                 ┌ cache.put ┐
  │  network chunk │ → hasher.update(chunk)  ← ここで   │  chunk を │
  └────────────────┘        │ 同期的に消費し切る MUST   │ transfer  │
                            └→ controller.enqueue(chunk)→│ しうる    │
                                                         └───────────┘
     src/sha256.ts:138-141  while (offset+64 <= len) compress(chunk, offset)  ← 同期消費
     src/sha256.ts:142-145  partial.set(chunk.subarray(offset))              ← 余りは copy
     ⇒ update() から戻った時点で chunk への参照はゼロ（= 非保持）。この性質が契約。
  ```

- **修正案**:
  1. ★`Sha256Hasher.update` の JSDoc に RFC 2119 で明記する（例: 「`update` は同期的に消費し
     切り、**リターン後に `chunk` を参照しない MUST** — 呼び出し側が enqueue / transfer /
     バッファ再利用をしても安全であることに `prefetchUrl` が依存する」）。1 行で済み、
     設計意図が読み手に残る。
  2. 1 に加えてテストで縛る: update 後にチャンクの中身をゼロで上書きしてから次の update を
     続け、一括結果と一致することを assert（保持していれば落ちる）。ミュータント殺傷力が付く。
  3. 対処しない（現状の実装で成立しているため）。
- **リスク**: 案 1 は無リスク（コメントのみ）。案 2 はテスト 1 本追加のみで実行時間は無視できる。
  案 3 は将来の最適化でサイレントに壊れる経路を放置する。
- **対象**: `src/sha256.ts:107-115`（`Sha256Hasher` の JSDoc）。依存側は `src/mod.ts:632-634`。
- **影響範囲**: ドキュメント / テストのみ。公開 API 非影響。
- **引き継ぎ（実装者向け）**: 案 2 のテストは `update(view)` の直後に `view.fill(0)` して
  一括ダイジェストと突合する形で書ける。ただし `partial` にコピーされる末尾 63 バイト以下も
  同時に守りたいので、**チャンク長が 64 の倍数でないケース**（例: 100 バイト × 3 回）を必ず
  含めること。
- **裁定（閉じた選択肢）**: **(a) 案 1 のみ（JSDoc に MUST を追記）** /
  **(b) 案 1 + 案 2（テストでも縛る）** / **(c) 対処しない**。

### B-3 (L) `hex()` が `schedule` スクラッチを `update` 経路と共有している（現状は安全）

- **概要**: `hex()` の最終ブロック圧縮（`src/sha256.ts:161-163`）は、`update` 経路と同じ
  `schedule`（`src/sha256.ts:120`）を渡す。`state` は `slice()` で複製しているのに
  `schedule` は共有、という非対称。**現状は安全** — `compress` は毎回 `schedule[0..15]` を
  ブロックから全上書きし、`[16..63]` はそこから導出するのでブロック間のキャリーオーバーが
  一切無い。かつ `hex()` は同期関数なので `update` と交錯しない。ただし「なぜ state だけ
  複製すれば十分なのか」がコード上どこにも書かれておらず、`schedule` を前ブロックから
  引き継ぐ最適化や `update` の非同期化を入れた瞬間に「`hex()` を呼ぶと以降のダイジェストが
  壊れる」という再現しにくい欠陥になる（`hex()` の非消費契約 = `src/sha256.ts:110-113` は
  この点を state についてしか保証していない）。
- **修正案**: ★`src/sha256.ts:159` のコメントに「`schedule` は共有でよい（compress が
  16 語を全上書きするためブロック間依存が無い）」を 1 行足す / または `hex()` 内で
  `new Uint32Array(64)` を確保する（finalize は最大 2 ブロックなので確保コストは無視できる）。
- **対象**: `src/sha256.ts:120, 159-163`。**影響範囲**: 内部のみ。
- **裁定**: **(a) コメント 1 行を足す** / **(b) `hex()` 内でスクラッチを別確保する** /
  **(c) 対処しない**。

### B-4 (L) 長さの下位語だけ 2^50 バイト超で double 精度を失う（実用上は到達不能）

- **概要**: 上位語は `Math.floor(totalBytes / 0x20000000)`（`src/sha256.ts:156`）で
  **2 の冪による除算 = 厳密**、`totalBytes <= 2^53` まで正しい。一方下位語は
  `(totalBytes * 8) >>> 0`（`src/sha256.ts:157`）で、`totalBytes > 2^50`（1 PiB）だと
  `totalBytes * 8` が 2^53 を超えて丸められ、下位ビットが落ちる。到達不能なので実害はゼロ
  だが、上位語だけ 2^53 まで正しく下位語が 2^50 で崩れるという**非対称が意図的なのか
  たまたまなのかコードから読めない**（`src/sha256.ts:152-154` のコメントは
  「下位は ToUint32 が mod 2^32 を取るのでそのまま」としか書いておらず、乗算前の丸めには
  触れていない）。
- **修正案**: ★`(totalBytes % 0x20000000) * 8` にすると乗算前に 2^29 未満へ落ちるので
  `totalBytes <= 2^53` まで上位語と同じ精度になり、非対称そのものが消える（コスト同一）。
  / または「Number の安全域 2^53 バイトを超える入力は非対象」とコメントに明記する。
- **リスク**: 式の差し替えは 1 行だが、SHA-256 の心臓部なので変更後は B-1 の 512MiB 突合を
  含めて再検証すること（`% 0x20000000` は `totalBytes` が 2^29 の倍数のときに 0 になる —
  正しい挙動だが off-by-one を作りやすい形なので、`0x20000000` ちょうどのケースを必ず通す）。
- **対象**: `src/sha256.ts:157`。**影響範囲**: 内部のみ。
- **裁定**: **(a) 式を `(totalBytes % 0x20000000) * 8` に変える（要 512MiB 再突合）** /
  **(b) 前提をコメントに明記するだけ** / **(c) 対処しない**。

## 横断所見（担当範囲から見た所見。他グループの領分には踏み込まない）

- **CLAUDE.md の「実行時依存ゼロ MUST」は守られている**: `src/sha256.ts` は
  `Uint32Array` / `Uint8Array` / `DataView` / `Math` のみ。import ゼロ。テスト側の
  `@std/assert` と `crypto.subtle` はテスト専用で publish 対象に入らない。
  `deno.json:5-8` の exports にも `./sha256` は無く、`Sha256Hasher` / `createSha256` の
  `export` はモジュール内部用（`src/mod.ts:20` からのみ）。**公開 API 表面は増えていない**
  ので、下流 yomi / sbv2-web への破壊的変更リスクはこの担当範囲からは発生しない。
- **「ネットワークに出るテスト禁止」も遵守**: `src/sha256.test.ts` は fetch も caches も
  触らない純粋な計算テスト。決定的 PRNG（`src/sha256.test.ts:17-25`）で失敗の再現性を
  確保しているのは良い設計判断で、`Math.random` を避けた理由がコメントに書かれている。
- **テスト設計の質は高い**: ①native との差分（実装バグ検出）②既知ベクタ
  （`src/sha256.test.ts:95-107`、native と純 TS が同じ誤解で共倒れする事態の検出）
  ③`hex()` 非消費（`src/sha256.test.ts:84-93`）の 3 層が揃っていて、ミューテーション試験でも
  9 種中 8 種を殺せた。殺せなかった 1 種が B-1 で、これは「テストの質」ではなく
  「凍結範囲」の問題。
- **性能はスコープ外（実測裁定済み）** の指示に従い評価していない。ただし
  `prefetchUrl` が `hex()` を flush と body===null 経路でしか呼んでいない
  （`src/mod.ts:619, 638`）ことは確認した — チャンク毎に `hex()` を呼ぶ（= 毎回パディング
