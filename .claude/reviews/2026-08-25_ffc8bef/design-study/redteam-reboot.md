## 評定

**Design R（提案どおり全部入り）: 非推奨（確信度: 中）**
ただし「sha256 の有無で戦略を型ごと分ける」という**核の直観は正しく、支持する**。非推奨なのは R を C から差別化している 3 要素 —— ①裸 sha256 キー ②公開キー/プレフィックス管理面の全廃 ③0.5.0 での B2（revalidate）実装 —— で、この 3 つを外すと R は実質 Design C に収束する。つまり「R を殺す単一の致命傷」ではなく、**R 固有部分がことごとく損な取引**という評定。

## 致命傷（採用すると後で構造的に泣く）

**F1. B2 の 304 は「メタデータを更新できない」— 数 GB では原理的に回らない**
Cache API にはエントリのヘッダだけを書き換える API が無い。`cache.put` は Response 丸ごとの置換であり、304 受信後に新しい `ETag`/`Date` を反映するには**キャッシュ本体 N バイトを読み戻して再 put** するしかない（4 GiB モデルで read+write 8 GiB の I/O）。実装は現に `storableResponse`（src/mod.ts:368-378）と prefetch 側（src/mod.ts:882）で**元レスポンスのヘッダを全部捨てて新 Response を組んでいる**ので、B2 は保存形式の変更（validator の焼き込み）から必要になる。結果、現実解は「304 でもメタデータを更新しない」しかなく、そうすると `max-age` 由来の鮮度寿命を持てない ⇒ **毎回必ず 1 RTT**。HF main ブランチ運用で起動毎にファイル数ぶんの RTT を払い、オフラインでは即死する。ADR 0006 が B2 を「予約のみ」に留めたのは正しい判断で、R はそれを撤回する理由を示せていない。

**F2. B2 のヘッダ焼き込みは Cache API 仕様の地雷を踏む**
validator を残すために元ヘッダをそのまま写すと、(a) `Vary: *` を含む応答は `Cache.put` が **TypeError で reject**（仕様の put アルゴリズム）、(b) `Vary: Accept-Encoding` 等が残ると `match` の照合に varied header 比較が入り、現在の「URL 文字列だけで必ず引ける」不変条件が崩れる、(c) `Content-Encoding`/`Content-Length` を写すと fetch が解凍済みのバイト列と矛盾したエントリになる。**`etag` / `last-modified` のみのホワイトリスト複写が MUST** で、これは設計文書に書かれていない実装制約。

**F3. 裸 sha256 キーは「次に来る lifecycle/GC ADR」を自分で塞ぐ**
ブリーフは「CAS + メタデータは GC と好相性か」と書くが逆。GC に要るのは **last-used 時刻 = 更新され続けるメタデータ**で、F1 と同じ理由（ヘッダ単独更新不可）から**ヒットのたびに N バイト再 put しないと記録できない**。回避策は「小さなメタ用エントリを別キーに持つ」だが、ブリーフ自身の制約「2 エントリ書き込みのトランザクションは無い」に真正面から当たり、**メタ孤児 / 本体孤児**という現行に無い不整合クラスを新設する。しかも取得元 URL をヘッダに焼く案は**最初の書き手の URL しか残らない**（同一内容の 2 回目は put されない）ため、一覧に出る provenance は恒常的に嘘をつきうる。

## 重い条件（呑めるなら R 可、呑めないなら非推奨のまま）

**H1. 「この repo のキャッシュを消す」が表現不能になる**
裸 hash キーでは `Cache.keys()` は不透明な hex 列しか返さず、repo で絞るには全エントリを `cache.match` してヘッダを読む線形スキャン（body は読まないので現実的だが、判定材料が F3 の嘘つき provenance）。加えて**クロス repo dedup の必然として「その repo だけ消す」は意味論的に成立しない**（同じエントリを他 repo が参照している）。0.4.0 が持っていた `cacheName` 隔離も、承認済み 0.5.0 のキープレフィックス隔離も両方失われ、**残る一括操作は `clearCache()` だけ**。同じライブラリで他の資産もキャッシュする下流アプリには明確な能力後退で、公開済み API での二重 breaking になる。→ 条件: repo/path を含む内容キー（= 0.5.0 現行 `["hf",kind,repo,path,sha256]`）を捨てないこと。dedup で得るのはストレージだけで、帯域は内容キーで既に取れている。

**H2. 2 キー空間は「同一バイト列の二重ダウンロード」を構造化する**
`sha256` 有無で join キー（src/mod.ts:663）が変わるため、同じファイルを sha256 付き/無しで呼ぶ 2 経路は **single-flight で合流せず、4 GB を同時に 2 本引き、2 エントリで 8 GB 消費する**。現行にも同型の穴はあるが、現行は公開 `key` で呼び出し側が明示的に統一できる。R はその逃げ道を消したうえでモード分岐を型で固定するので、**回避手段が無くなる**。とくに `prefetchUrl` は sha256 を渡さないと URL キーに入り（src/mod.ts:781-783）、後続の Mode A 読み出しに**絶対にヒットしない** ——「温めたのに再ダウンロード」は本命ユースケースの直撃。→ 条件: Mode A では prefetch の `sha256` 必須（未指定は throw）を仕様化。

**H3. Mode A の self-heal は「唯一の複製を先に消す」**
現行実装はヒット内容が検証に落ちると `cache.delete` → フォールスルーで fetch（src/mod.ts:526-539）。Mode A では URL が「ミスしたときの取得元」に降格し、失効しがちな URL（削除された revision・期限付き署名 CDN・消えたミラー）を渡す運用が奨励される。**ビット腐敗 1 件が「唯一のローカル複製を捨てたうえで 404」**に化ける。→ 条件: 取り直し成功後に差し替える（fetch-then-swap）へ変更。

**H4. revalidate は single-flight と原理的に噛み合わない**
sha256 は「バイト列の純関数」なので合流者が各自再判定できる（現行の設計はここに乗っている）。**鮮度はバイト列の関数ではない**ため、合流者は leader の revalidate 結果を追試できない。`revalidate: true` の呼び出しと `false` の呼び出しが同一 URL に並ぶと、**どちらが leader になるかで鮮度が変わる非決定**が生まれる。回避は「revalidate 指定は合流しない」= 二重ダウンロード。どちらも文書化必須の新たな限界。

**H5. ネットワーク不達時の既定が規約と衝突する**
CLAUDE.md の「正規の縮退経路は 2 つだけ（self-heal / onCacheError）」に、revalidate 失敗時の stale-if-error は**第 3 の縮退**として入る。一方 fail loud 一択にすると「cache I/O 失敗は network へ縮退する」の対称形（network 失敗は手元へ縮退）を否定することになり、ブラウザ/オフライン用途では明確に敵対的。**どちらを採っても既存 ADR（0001）の書き換えとオプション追加（`staleIfError`）が要る** ——「オプション面を減らす」という R の売りを自分で削る。

**H6. 工数見積りは甘い**
ffc8bef で消えるのは直列化まわり約 100 行（`serializeKey`/`deserializeKey`/`serializePrefix`/`matchesPrefix`/`evict`/`listKeys`）で、削除自体は安い。高いのはその外側: 139 本のテストのうち key/prefix/`HfFileSpec.key` 由来のものは書き直し、採用直後の **ADR 0006 は supersede + 新 ADR**、README のキー粒度表・limitations・0004/0005 の相互参照（すべて「キー」語彙で書かれている）も追随。B2 を入れるなら保存形式変更 + F2 のホワイトリスト + 条件付き GET の DI テスト（304 を返す偽 fetch、`init` 由来の If-None-Match 衝突、Range/206）が丸ごと新規。「ほぼリブート OK」でも**docs 工数が実装工数を超える**構図は変わらない。

## 軽微（R 固有ではない / 文書化で足りる）

- **誤った sha256 を渡し続けるケース**: 毎回 N GB を落として不一致 throw、negative cache は無い。現行 ffc8bef と完全に同じ挙動なので R の減点ではない。ただし Mode A では「hash を外して素で取る」逃げが**別モードへの呼び出し変更**になる点だけ悪化する。
- **内容キーの安全性は R の素直な利点**: バイト検証があるのでミラー跨ぎ共有は安全。逆に「private repo のバイトが hash を知る全呼び出し元から読める」（合流者の `init` は使われない — src/mod.ts:589-591 の既知制約の延長）は R で射程が repo/ミラー跨ぎに広がる。ローカル単一ユーザー前提なら受容可だが limitations.md 追記は MUST。
- **`VERSION` は src/mod.ts:30 でまだ `"0.4.0"`**（ffc8bef 時点、bump 前）。R を採るなら未リリースのまま差し替えられるので、リリース済み API 制約はかからない —— R の唯一の「今なら安い」根拠であり、逆に言えば**この窓を根拠に急いで B2 まで入れる必要はない**（B2 は非破壊の後付けが可能）。
- DevTools の Cache Storage 可読性（ADR 0006 が明示的に評価した性質）は裸 hash で失われる。運用上の痛みは小さいが、意図的に捨てる判断として記録すべき。

## 推奨（赤チームとしての着地点）

1. **モード分離は採る**（sha256 有無で型を分ける／`sha256` と `revalidate` の併用は throw）。
2. **キーは `["sha256", <hex>]` ではなく repo/path を残した内容キー**を既定に（= 現行 ffc8bef の HF 既定そのまま）。裸 hash による dedup は F3/H1 に対して割に合わない。
3. **B2 は 0.5.0 で実装しない**。F1/F2/H4/H5 は独立した ADR 1 本ぶんの重さがあり、非破壊で後から足せる。
4. 公開 `key` の撤去（＝ ADR 0006 §5 の脚砲を構造的に消す）と `HfFileSpec.key` の廃止は**支持する**。ただし `listKeys`/`evict(prefix)` は内部キー体系が残る以上そのまま残せるので、管理面まで削る理由は無い。
5. 採用の可否に関わらず **H3（fetch-then-swap）と H2（prefetch の sha256 必須化）は現行 ffc8bef にも効く修正**。

（推測ラベル: HF の resolve URL が CDN リダイレクト先で If-None-Match を honor するか、304 を返すか、`Vary` を付けるかは未検証の推測。B2 を検討するなら実 HTTP 応答ヘッダの実測が前提条件になる。）
