# 0010 — 429 / 503 は Retry-After に従って既定で再試行する

- 日付: 2026-09-05
- 状態: 採用
- 関連: [0001](0001-cache-io-degrade-with-notification.md)（縮退の許される範囲）/
  [0002](0002-request-init-passthrough.md)（`init` パススルー = AbortSignal の出どころ）/
  [0004](0004-single-flight-raw-sharing.md)（リスナー throw の隔離方針）

## Context

取得の失敗はこれまで一律に fail loud だった。HTTP エラーは 3 か所（`fetchBytes` の network
経路・`prefetchUrl`・`resolveHfRevision`）で応答を受け取った直後に throw していて、ステータスに
よる区別は無い。

そこへ 2 つの事実が重なった。

1. **1 回の起動あたりの要求数が増えた。** 下流は単一 ArrayBuffer 上限（ADR 0007）を避けるため
   重みを shard へ分割しており、1 モデルの読み込みが数十本の要求になる。加えて可変 ref では
   ファイル毎に revision 解決の要求が先行する。
2. **HuggingFace Hub は rate limit を 429 で返す。** 429 は「今は多すぎる」であって「取れない」
   ではない。数十本のうち 1 本が 429 を踏んだだけで、それまでに温めたぶんを含めて起動全体が
   落ちる — しかも `Retry-After` で待つべき秒数まで教えられているのに捨てている。

429 / 503 に対して即 throw するのは、**サーバが明示した「後で来い」という指示を無視して失敗に
変える**ということで、fail loud の趣旨（不正を握り潰さない）とは別物である。

## Decision

### 1. 対象は「後で成功しうる」ことがステータスで分かるものだけ

既定 `[429, 503]`。`RetryPolicy.statuses` で変更できる。接続エラー・受信途中の切断・その他の
4xx / 5xx は対象外で、従来どおりそのまま throw する — 再試行が成功に転じる根拠が無く、副作用の
ある要求を盲目的に打ち直すことにもなるため。

同じ理由で**対象は GET / HEAD だけ**とする（`init.method` 省略時は GET）。`cache: false` の
呼び出しは任意の method を通せる（ADR 0002）ので、method を見ないと `POST` + body の要求が
429 / 503 で打ち直されてしまう — 冪等でない要求の再送はライブラリが黙って決めてよいことでは
ない。GET / HEAD 以外は最初の応答をそのまま返し、呼び出し点が従来どおり throw する。

### 2. 待機は Retry-After 優先、無ければ指数バックオフ

`Retry-After` は delta-seconds（非負整数の秒）と HTTP-date（現在時刻との差・過去なら 0）の
両形式を読む。HTTP-date として `Date.parse` に渡すのは**曜日名で始まる値だけ**とする — RFC
9110 の HTTP-date 3 形式（IMF-fixdate / RFC 850 / asctime）はいずれも曜日名で始まるのに対し、
V8 の `Date.parse` は `"1.5"` / `"+120"` のような数値系の書式ミスを 2000 年前後の日付として
受理してしまい、渡すと「過去 → 待機 0」に化けて rate limit 中の相手へ待機ゼロで連打すること
になるためである。どちらとしても解釈できない値は「指示なし」へ落とす（サーバの書式ミスで
取得を落とさない）。指示が無ければ `baseDelayMs * 2 ** (attempt - 1)`（既定 1, 2, 4, 8, 16 秒）。
`maxDelayMs` を渡したときだけ**サーバの指示にも**上限が掛かる — 省略時は指示どおり待つ。
既定の上限を勝手に決めないのは、Hub が返す長い待機ほど「その時間待たなければ通らない」ことを
意味するからで、勝手に短く切れば再試行を消費するだけになる。

ただし `setTimeout` が扱えるのは符号付き 32bit（`2**31 - 1` ms ≒ 24.8 日）までで、これを超える
指定は実装が 1 ms に潰して**即時発火**する（Deno は `TimeoutOverflowWarning` を出す）。
`Retry-After: 2592000`（30 日）や数週間先の HTTP-date がそのまま「待たない再試行」になり、
サーバの指示を無視して打ち直すことになる。**守れない待機は再試行しない** — `maxDelayMs` 適用
後の待機が上限を超えるときは**そのラウンドの応答**をそのまま返し、そのラウンドは再試行回数に
数えず `onRetry` も呼ばない。それまでに再試行していれば `retries` にはその回数が残るので、
呼び出し点の文言末尾には `（再試行 N 回の後）` が付く（「最初の応答」がそのまま返るのは
GET / HEAD 以外を再試行しない §1 の経路だけ）。短く切って打ち直したいなら `maxDelayMs` を
渡す＝呼び出し側の明示的な選択にする、という §2 の判断をそのまま延長した形である。

### 3. 既定で有効・`retry: false` で opt-out

`retry` 省略時に既定値が効く。「rate limit に当たったら待って取り直す」は呼び出し側が毎回書く
定型であり、書かなかった場合の既定として正しいのは「待つ」の側だと判断した。待ちたくない
呼び出し（対話的な UI 等）は `retry: false` で従来の挙動へ戻せる。

### 4. throw そのものは呼び出し点に残す

再試行は `src/retry.ts` の `fetchWithRetry` 1 本に集約し、3 か所の呼び出し点が全てそこを通る。
ただし**使い切ったときは最後の応答をそのまま返し**、`!response.ok` の throw は従来どおり
呼び出し点で行う。文言 `fetch-cache: HTTP {status} {statusText} ({url})` の先頭は変えず、
再試行した場合だけ末尾に `（再試行 N 回の後）` が付く（下流は先頭一致で判別している）。

接尾辞が付く条件は「再試行が 1 回以上走った」ことだけで、**最終ステータスが 429 / 503 とは
限らない**。対象ステータスで待って取り直した結果が対象外のエラーになった場合（例: 429 → 待機
→ 404）、そのラウンドで回数を持ったまま応答が返るので、404 の文言に `（再試行 1 回の後）` が
付く。回数は「何回打ち直したか」であって「最後に何を踏んだか」ではない。

### 5. 通知と中断

`onRetry` は待機の**前**に 1 回ごと呼ぶ（`{ url, status, attempt, delayMs, retryAfter }`）。
リスナーの throw は取得を落とさない（console.warn して続行 — `onProgress` と同じ隔離。
ADR 0004）。待機は `init.signal` で中断でき、既に aborted なら待たずに `signal.reason` で
reject する。MUST: 待機完了時に abort リスナーを外し、abort 時に timer を clear する
（残すとリークになる）。

HF 層では `init` と同じ扱いで **revision 解決とファイル取得の両方**へ透過する。

### 6. `RetryPolicy` の値は要求の前に形式検査する

`retry` に渡された値は `fetchWithRetry` の入口で検査し、外れていれば network に出る前に throw
する（`sha256` / `expectedBytes` と同じ fail loud。文言は
`fetch-cache: retry.<field> は … で指定してください: <値> (<url>)`）。受理するのは
`maxRetries` が 0 以上の整数、`baseDelayMs` / `maxDelayMs` が 0 以上の有限数、`statuses` の各
要素が 400〜599 の整数。

黙って受けると §2 / §3 の MUST が裏返るためである。`NaN` は `Math.min` を通っても `NaN` の
ままで `NaN > MAX_TIMER_MS` が偽になり、「守れない待機は再試行しない」ガードを素通りして
待機ゼロの連打になる。`maxRetries: NaN` は `attempt >= NaN` が恒偽で、回数では止まらなくなる。
2xx を `statuses` に入れる誤設定も同じ入口で弾く（成功応答を捨てて打ち直すことになる）。
検査の位置は `fetchWithRetry` なので、キャッシュヒットで決着する呼び出しでは throw しない
（network に出る直前で落ちる）。

### 7. 待機に jitter は入れない

待機は `Retry-After` の値、無ければ `baseDelayMs * 2 ** (attempt - 1)` で、乱数成分を持たせ
ない。`fetchHfFiles` が全 spec を `Promise.all` で並列取得する以上、rate limit を踏んだ N 本が
同じ待機を取って次の波も揃って届く（thundering herd）ことは承知のうえで、0.7.0 では入れない。

理由は 3 つ。①同期した群れを作っているのは再試行ではなく**初回の fan-out**であり、jitter が
散らせるのは「429 の後に同じ波形を繰り返す」ぶんだけで、429 を誘発する最初の波は変わらない。
根治は `fetchHfFiles` の並行度上限で、それは公開 API を増やす別の設計判断になる。②Hub の rate
limit が瞬間同時数と時間窓クォータのどちらで効いているかを計測していない。後者なら jitter を
足しても全本が窓明けに揃うだけで効果が薄い。③既定 ON の jitter は文書化した 1 / 2 / 4 / 8 /
16 秒と `RetryContext.delayMs` の観測値を変えてしまう（呼び出し側が待機時間を検査できる面で
あり、0.7.0 の「追加のみ」から外れる）。実利用のフィードバックが溜まった時点で再検討する。

## Consequences

- **観測可能な挙動変更は 429 / 503 の応答時だけ**（それ以外の応答は 1 回目の結果がそのまま
  返る従来どおりの経路）。API は追加のみで、既存の型・関数・エラー文言の先頭は不変 — minor
  リリースとして出せる。
- 429 / 503 を「即失敗する見本」として使っていたテスト fixture は非対象ステータス（500）へ
  移した。挙動の変化がそのまま現れる箇所であり、意図どおり。
- 失敗が遅くなる。恒久的に 503 を返すサーバに対しては、**`Retry-After` が無ければ**既定で
  最大 31 秒（1+2+4+8+16）待ってから落ちる。`Retry-After` 付きなら上限は掛からず、指示どおりの
  待機が最大 `maxRetries` 回（既定 5）**累積する** — `Retry-After: 3600` を返し続けるサーバなら
  合計 5 時間になる（§2 の「既定の上限を置かない」判断の帰結）。急ぐ呼び出しは `maxRetries` /
  `maxDelayMs` を絞るか `retry: false` を渡す。
- single-flight の合流者は leader の再試行をそのまま待つ（合流の契約は変えていない）。
  合流者の `retry` / `onRetry` は leader のそれで走っている取得には効かない（`init` /
  `expectedBytes` と同じ既知の制約 — docs/limitations.md）。
