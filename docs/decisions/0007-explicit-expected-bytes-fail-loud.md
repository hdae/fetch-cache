# 0007 — 明示 `expectedBytes` の確保失敗は縮退させず fail loud

- 日付: 2026-08-25
- 状態: 採用
- 関連: [0001](0001-cache-io-degrade-with-notification.md)（縮退の許される範囲）/
  [0005](0005-streaming-prefetch-and-verified-marker.md)（`expectedBytes` の導入）

## Context

`expectedBytes` は受信バッファの事前確保ヒントで、確保できなければ「ヒント無し」へ縮退して
チャンク蓄積経路へ委ねる設計だった（0005）。申告は検証ではないので、外れても取得を落とさない
というのが一貫した方針である。

ところが蓄積経路の終端は同じ長さの連結バッファを 1 本要求する
（`readBody` の `new Uint8Array(loaded)`）。つまり**確保できなかった理由が「そのサイズを確保
できない実行環境だから」だった場合、縮退しても最後に同じ理由で落ちる** — 違いは「全量を
ダウンロードし切った後で落ちる」ことだけで、帯域を丸ごと捨てる。

これは机上の縁ケースではない。Chromium は単一 ArrayBuffer を 2,145,386,496 バイトで意図的に
打ち切るため、それを超える単一ファイル（下流の推論スタックには 3,913,609,588 バイトの重みが
実在する）はこの経路に必ず乗る。モバイル回線で 3.9GB を受け切ってから
`RangeError` で落ちる挙動になっていた。

## Decision

`readBody` の確保失敗の扱いを、申告の出どころで分ける。

### 1. 呼び出し側が `expectedBytes` を**明示**した場合は縮退せず throw

確保が落ちたら body を `cancel()` して（未消費 body は接続リソースを保持するため）、受信を
1 バイトも始めずに throw する。文言には要求サイズ・取得元 URL と「実行環境の単一 ArrayBuffer
上限を超えている可能性」を載せ、`cause` に元の `RangeError` を残す。

「取得は落とさない」という 0005 の約束はここでは守れない — 縮退しても同じ理由で落ちるのだから、
守れているのは*落ちる時刻を遅らせること*だけであり、それは呼び出し側にとって害でしかない。

### 2. content-length 由来の確保失敗は従来どおり縮退する

サーバ申告は信頼しない（0002 以来の方針・docs/limitations.md）。**実受信が上限に収まるなら
取得は成立する**ので、ここで落とすのは誤検知になる。非対称は意図的で、判断の根拠は
「その数字を誰が主張したか」である。

### 3. 形式不正の申告（非整数・0 以下）は従来どおり「ヒント無し」

確保を試みる前の入口ガードであり、確保失敗とは別分岐。挙動は不変。

## Consequences

- **観測可能な挙動変更**。ただし変わるのは「元々落ちていた呼び出しがいつ落ちるか」だけで、
  成功していた呼び出しの挙動は 1 つも変わらない（確保が通れば従来と同一経路）。唯一の例外は
  「確保不能なほど大きい `expectedBytes` を明示しつつ、実受信は小さかった」呼び出しで、
  これは申告そのものが呼び出し側のバグなので fail loud が正しい。
- 「申告が外れても取得は落とさない」という limitations の記述に、確保失敗だけの例外が付く。
  長さの**検証**に使わない点は不変（`validate` の担当のまま）。
- 上限を超える単一ファイルを扱う下流は、この throw を受けて分割配布・streaming 経路
  （`prefetchUrl` + shard 毎の `fetchBytes`）へ設計を寄せることになる。ライブラリ側が
  黙って肩代わりできる問題ではないので、失敗を早く正確に見せることを選ぶ。
