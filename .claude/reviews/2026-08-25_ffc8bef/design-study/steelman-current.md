## 評定

**Design R: 非推奨（確信度: 中）** — ただし「現行 ffc8bef をそのまま出す」ではなく **Design C への収束**を推す。R が真に独占する便益は「モード排他の型レベル表現」1 点で、それ以外（脚砲の消滅・内容 dedup・304）は C が現行基盤の上で回収できる。逆に R は、レビューで欠陥ゼロだった層（キー直列化）を捨てつつ、**列挙・掃除の I/O コストと構造性**を確実に失う。確信度が「高」でないのは、GC（寿命軸）をメタデータヘッダ方式で作ると決めた瞬間に後述の決定的論拠①が半減するため。

---

## 論拠の格付け

### 決定的

**① 列挙・掃除の情報が「キーの中」にあるか「エントリの中」にあるかは、Cache API 上では I/O 量の差である。**
Cache API の列挙は `Cache.keys(): sequence<Request>` しか無く、**レスポンスヘッダは `keys()` から読めない**（読むには 1 件ずつ `cache.match` して Response を開く必要がある）。現行は `src/mod.ts:1005-1024` のとおり `keys()` の URL 文字列を `deserializeKey` するだけで構造化キーが全件返る（body を一切開かない）。R の `listCached(): { mode, key, sourceUrl?, storedAt? }[]` は原理的に **N 回の `match` + N 個の Response の後始末**になる（本リポジトリ自身、未消費 body がハンドルを保持する事実を前提に `src/mod.ts:806`・`:543` で明示 cancel している）。数 GB × 数十エントリの環境で「一覧を出す」「掃除 UI を描く」が body オープンを伴う操作に降格するのは、R が構造的に負う恒久コスト。

**② 「repo Y のキャッシュを全部消す」が R では表現不能になる。**
現行: `evict(["hf","model","org/repo"])` — `keys()` 1 パス・前方一致・0 body read（`src/mod.ts:986-998`、境界はセグメント厳密 `matchesPrefix`）。R: キーが裸の sha256 なので、**ハッシュを全部知らない限り部分削除ができない**。listCached でメタデータを読み、`sourceUrl` を文字列マッチして選別する経路に落ちる（型無し・last-writer-wins のメタデータ依存）。オーナーが次に予定している寿命軸（TTL / 未使用 1 週間 GC）は「何を残し何を消すか」の**グルーピング**が本体であり、CAS は dedup には最適だが**グルーピング情報をキーから抹消する**。ブリーフの「CAS + メタデータは GC と好相性か」は、この点で少なくとも片面的だと考える（①の I/O も同時に効く）。

**③ オーナーの未充足要求（304 / revalidate）はリブートでは一切安くならない。**
現行もRも `revalidate` は未実装で、必要な作業は同一: `storableResponse`（`src/mod.ts:368-378`）が現在 `SHA_HEADER` 以外の元ヘッダを**全部捨てている**ため、どちらの設計でも ETag / Last-Modified の写し取りと条件付き GET 経路を新規に書く。つまり R の工数のうち「新しい価値」に対応するのは revalidate だけで、残りは**既に動いている物の作り直し**。

### 相応

**④ 撤去対象は「欠陥が見つからなかった層」である。** `.claude/reviews/2026-08-25_ffc8bef/findings/core.md` の総評は、単射性・可逆性・セグメント境界・URL 正規化不変性を実測で崩せなかったと記録し（旧 IM-03 の問題クラスは消滅）、Critical 0 / Error 0。HF レンズも `defaultKey` 単一実装による 3 API のキー一致（HF-12）と内容キー配下の記録ハッシュ必在（HF-15）を構造保証として確認している。テスト資産は `src/mod.test.ts` 1969 行 + `src/hf/mod.test.ts` 1000 行。R はこの資産のうちキー機構に触れる部分を削除し、`single-flight` の TOCTOU 不変条件（`src/mod.ts:676-695` の「inflight.set まで await を挟まない」）や prefetch のチャンク複製（`:865`）・保険 delete（`:896-901`）を新しい鍵導出の上で**再度凍結し直す**必要がある。ただし未リリース・下流はどのみち移行という条件下では「サンクコスト」ではなく純粋な工数差なので、決定的ではない。

**⑤ 「キー × 完全性」の直交は、URL キーのままでの完全性検証を可能にしている。** 現行は `sha256` をキーと独立に指定でき、URL キーのエントリにも記録ハッシュが焼かれて self-heal が効く（`src/mod.ts:520-535`）。R の Mode B の完全性は `validate` / `expectedBytes` のみで、**ハッシュ既知だがキーは URL のままにしたい**（DevTools で読める・ミラーを跨がせたくない・監査で取得元を残したい）という選択肢が型ごと消える。実在性は中程度（推測: 主戦場の HF では内容キーで足りる）だが、汎用層の表現力としては明確な後退。

**⑥ Design C は R の便益の大半を非リブートで回収する。** C = 公開 `key`（`FetchBytesOptions.key` / `PrefetchUrlOptions.key` / `HfFileSpec.key`）の撤去 + 既定キーを内容キーに寄せる + revalidate 実装。オーナーの問題意識「戦略を分けなかった」の原因は**公開 key オプションが両戦略を混ぜられること**であって、配列直列化機構そのものではない。C は原因だけを切り、`evict`/`listKeys` を内部既定キーの管理導線として残せる（①②が保たれる）。残る一般性を「死んだ一般性」と呼ぶかは、上の掃除導線を価値と見るかで決まる。

### 弱い

**⑦ ADR 0006 §5 の脚砲は文書化で足りる、という擁護。** 発生条件は「呼び出し側が内容識別を含まない安定キーを**明示**した場合」のみで、既定経路（HF: sha256 有 → `["hf",kind,repo,path,sha256]` / 無 → revision 固定 resolve URL、`src/hf/mod.ts:208-212`）では**表現されない**。実害も再取得（帯域）であって誤配ではなく、fail loudly と self-heal の不変条件は保たれる。有界ストレージと引き換えの明示的トレードオフ。
— ただしこの擁護は自分で崩れる: CORE-004（`.claude/reviews/2026-08-25_ffc8bef/findings/core.md:160-`）は、「安定キー + sha256 + 単一 ArrayBuffer 上限超えファイル」で **prefetch は `false` を返して更新せず、`fetchBytes` は materialize できず throw（ADR 0007）**ため、`evict` を手で挟まない限り**更新経路が存在しない**ことを実測付きで示している。主戦場（数 GB）の中心付近に穴が開いている以上、「文書化で十分」は成立しない。R はこの穴を構造的に消す — ここは R の正当な得点であり、私の立場から見た最大の弱点。ただし C でも公開 key 撤去により同じく表現不能になる（脚砲は R 固有の便益ではない）。

**⑧ 型レベルの排他は R 固有の得点。** 現行は `sha256`/`recheck`/`key`/`cache:false` の矛盾組合せを実行時 throw で弾いている（`src/mod.ts:609-646`）。TS 規約「可能なら型で制約し、実行時チェックに落とさない」に照らすと R の判別可能ユニオンが上位。ただし ①②を捨てる対価としては軽い。

## 観点別の短評

1. **配列キーの実在ユースケース**: (a) アプリ名前空間分離 `["app", ...]` + 一括掃除 — R のメタデータ案では①②のコストで代替（実在性: 高）。(b) 「モデル Y を消して 12 GB 空ける」— R では代替が苦しい（実在性: 高）。(c) キャッシュ済み一覧 UI — R は N×match（実在性: 中）。(d) 版付きアセット `["asset", id, ver]` の共存/掃除 — R では sha256 を台帳で持てば代替可（実在性: 中）。
2. **§5 脚砲**: 発生確率は低い（明示 opt-in のみ）が、⑦のとおり最悪ケースが主戦場に落ちるため「文書化で十分」は擁護しきれない。**撤回する**。
3. **C の充足度**: 脚砲消滅・内容 dedup・304 のすべてを回収。未回収は⑧のみ。よって「C で十分 ⇒ R 不要」は成立すると判断する。
4. **将来軸との合成**: 寿命軸は R と衝突しないが、②のとおり**グルーピングをキーから失う**方向に働く。鮮度軸は現行のフラットな置き場（ADR 0006 §2 の `revalidate` 予約）で足り、R の 2 モード固定は「sha256 既知 × URL キー × 条件付き GET」を表現不能にする（⑤）。窮屈になる未来は**中程度の確度で存在する**（推測）。
5. **資産価値**: ④のとおり実体はあるが、未リリース + 下流はオーナー管理という前提では決定打にならない。

## 付記（この観点から外れるが決定に効く事実）

現行 W 群のうち **CORE-004 / HF-01 は R で構造的に消滅**する一方、**HF-04（`evict` / `listKeys` に `caches` DI が無い）と CORE-001（予約 origin ガードの大文字すり抜け、`src/mod.ts:229-235`）は R でも別の形で残る/再発しうる**（管理 API の DI 欠落は R の `evictSha256` / `listCached` にそのまま引き継がれる）。「リブートすれば W が片付く」は成立しない。
